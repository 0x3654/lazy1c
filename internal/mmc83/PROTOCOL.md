# MMC-протокол ragent 1С:Предприятие 8.3 — находки реверса

Управление кластером 8.3 без службы RAS (:1545): консоль кластера
(radmin.dll, «SrvrConsole») говорит с ragent:1540 тем же семейством
протоколов, что и 8.2. Документ — по эталонному захвату настоящей консоли
8.3.27.2325 против контейнера server1c-8.3.27.2325 (16.09.2026,
research/spy83-local.log, кадры — research/spy83-frames/, разбор
research/extract83.py + scan83.py). Захват снимался петлёй v3:
шпион на маке 10.211.55.2:3540 → localhost:1540, hosts VM `server1c` → мак.

## Каркас — тот же, что 8.2

- ragent здоровается первым: константные `53 F5 C6 1A 7B`.
- Трейлер каждого кадра: `66 53 B2 A6`.
- Keepalive: `21 47 54 B3` каждые 5 с.
- Бинарные запросы: `[41 95][16Б GUID-LE сессии][8f? <счётчик>][тело]`,
  ответы: `[42 8f <счётчик LE16>][тело]`.
- Текстовые кадры: BOM + 1С-текстовый кортеж `{0|1,<uuid>,<seq>,…}`.

## Рукопожатие (ПРОЩЕ 8.2 — один конверт, без отдельных NTLM-кадров)

```
S→C  5Б     приветствие 53 F5 C6 1A 7B
C→S  744Б   конверт [d7 00 <len LE>]: BOM+"n",{#base64:материал},{#base64:AQAB}
             + интро {0,<uuid клиента>,23015,4,<uuid>,…}:
             {"S","##AdminProcess##:##AdminProcess##"},
             {"S","SrvrConsole"},            ← приложение
             {"S","<клиент>"},                ← имя машины клиента
             {"#",671507fd-…,{#base64:NTLM-type1}},   ← NTLM type1 В КОНВЕРТЕ
             {"S","8.3.27.2325"},            ← версия клиента (сверяется!)
             {"S","1ru_RU"},{"S","1ru_RU"}
S→C  501Б   конверт-ответ (challenge внутри base64)
C→S  92Б    BOM{0,<uuid сессии>,23016,1,<uuid>}   ← uuid сессии ГЕНЕРИТ КЛИЕНТ
S→C  24Б    BOM{1,<id ответа>,96}                 ← 96 = ок
```

Проверено на чужой 8.3-стенд: несовпадающая версия → текст «Различаются версии клиента
и сервера (<клиент> - <сервер>), клиентское приложение: Консоль кластера»
(бесплатное чтение версии сервера!). Совпавшая версия + 8.2-конверт →
молчаливый разрыв: после совпадения сервер разбирает конверт «по-своему».
Отдельного 522-байтового NTLM3-кадра (как в 8.2) НЕ существует — реплей
8.2 против 8.3 именно поэтому ложил ragent.

## Мутация «запрет начала сеансов»

89-байтовый бинарный кадр `[41 95][GUID-LE]…`. Вкл/выкл различаются
**одним байтом тела**: `8D FE` = запрет, `8D 01` = разрешение
(тег `8D` — bool). В захвате поля «сообщение» и «код разрешения» были
пустые — строк в кадре нет; с заполненными полями ждём повторный захват
(ожидаемо `9a <len> <текст>` в теле).

## Словарь

Потоковый словарь как в 8.2: те же кадры работают только на сервере,
с которого сняты (реплей против другого кластера потребует своего набора).
Первые строки словаря приезжают в конверте/кластерном ответе.

## Операции (сняты и реализованы, 16.09 вечер)

- **terminate** (248Б): побайтный реплей кила консоли — кадр
  `research/spy83-frames/1353_…C2S_248.bin` (16.09, локальный стенд) совпадает
  с `tmplTerminate` без единого байта. Клиент меняет в клоне ровно ДВА uuid
  по 95-тегам: базу @0x69 и жертву @0x90. **Слот @0x7e — uuid оператора
  консоли из реплея — не трогать**: вписывание туда uuid пользователя жертвы
  ломает кил (сервер ackает 18Б, сеанс жив). Сообщение и счётчик — реплейные
  («Сеанс работы завершен администратором.», длина 97-строки в СИМВОЛАХ):
  собственная пересборка строки/счётчика тоже ломала кадр — проверено живьём.
  Ответ 18Б ack (ничего не гарантирует —ACK есть и по несуществующей жертве),
  4Б голый трейлер = кадр отвергнут (нет словаря). Кадр ссылается на
  потоковый словарь: отправлять только после цепочки кластеры → базы →
  полный список сеансов (как FetchAll у 8.2).
- **роли uuid в записи сеанса** (решено по эталонному килю): перед именем
  базы 2–3 uuid; **ПОСЛЕДНИЙ = база, ПРЕДПОСЛЕДНИЙ = сеанс** (первый, если
  он есть, — служебный, принадлежит соседней записи/подключению). Прежнее
  «ids[0] = сеанс» путало роли в трёхuuid-записях: кил уходил по чужому
  uuid — сервер ackал, сеанс жил. Живо проверено: килы по обеим формам
  записей подтверждаются исчезновением из свежего опроса.
- **полный список сеансов** (112-кадр): все записи с uuid — источник uuid
  для terminate; по-базовый список — 128-кадр с uuid базы (uuid в списке
  баз принадлежит СЛЕДУЮЩЕЙ записи — проверено и RAS-сверкой).
- **toggle запрета начала сеансов** (89Б): подтверждён на 5 экземплярах —
  тело всегда одинаковое, значение не передаётся, сервер переключает сам.
- списки (сняты, ролей достаточно для TUI): рабочие процессы+менеджеры
  (150→7846), лицензии (134→5736), соединения (88→437, 128→438),
  свойства центрального сервера (89→134).
- 147-кадр (открытие диалога свойств с параметрами): строки сообщения/кода
  в трафике ОТСУТСТВУЮТ — параметры блокировки консоль в кадры не кладёт
  (либо канал иной). Загадка открыта.

## Сессийная привязка реплея (16.09, вечер)

Проба чтения против чужого сервера 8.3.27.1688: версия НЕ главное
препятствие — сервер не отвечает «различаются версии», а отвергает
рукопожатие «Сеанс работы завершен администратором» (бэктрейс rtrsrvc).
Эксперименты с uuid:
- uuid сессии (40a107f8) СГЕНЕРИРОВАННЫЙ — отвергается ДАЖЕ своим
  сервером → uuid связан с шифро-материалом конверта (RSA) или выдаётся
  сервером в конверт-ответе (тот бинарный, base64-маркеров нет);
- прочие uuid (e23134a2/7f58f27d/bc9113bc/73cdaa77) — константы,
- diag192 — ТЕКСТОВЫЙ кадр: LE-патч головы портит его uuid-строку.

Вывод: формат операций одинаков между версиями; чужой сервер требует
СОБСТВЕННОГО крипто-конверта (как и в 8.2 — см. «чего нет»). До этого
реплей mmc83 работает только с сервером-донором шаблонов.

## Чего пока нет

Мутации РЗ; чтение состояния блокировок (34Б-ответ всегда 81×4 — не флаги);
быстрый опрос (Poll = новое соединение); парсеры процессов/лицензий/соединений
(кадры сняты — дело техники).
